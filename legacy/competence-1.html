SAÉ 2025/2026 — Développement Web

Coup de Sifflet

Cette SAÉ consistait à développer une application web de gestion électorale permettant d'organiser et de superviser un processus de vote en ligne dans un contexte sportif — l'élection d'une équipe européenne. Le projet intègre des exigences de fiabilité, de sécurité et de conformité juridique (RGPD, propriété intellectuelle).

Fonctionnalités

  • Inscription et authentification des électeurs
  • Gestion des rôles (électeur / administrateur)
  • Système de vote en ligne sécurisé
  • Anonymat du vote (séparation identité / bulletin)
  • Unicité et impossibilité de modification du vote
  • Publication des résultats à la clôture du scrutin

Technologies

  • Application web (HTML, CSS, JavaScript)
  • Backend avec base de données relationnelle
  • Requêtes SQL sécurisées
  • Hachage des mots de passe
  • Gestion des accès par rôles
  • Conformité RGPD et loi Informatique et Libertés

Cadre juridique

  • RGPD — Règlement (UE) 2016/679
  • Loi Informatique et Libertés n°78-17
  • Code de la propriété intellectuelle (CPI)
  • Recommandations ANSSI
  • Mentions légales et CGU intégrées
  • Minimisation des données collectées

Retour sur la SAÉ Coup de Sifflet

Ressources mobilisées

J'ai mobilisé les cours de développement web, de bases de données et de droit du numérique. J'ai également consulté la documentation officielle du RGPD, les recommandations de la CNIL et les guides de l'ANSSI pour la sécurisation des applications web.

Points forts

La réflexion juridique menée en parallèle du développement m'a permis de mieux comprendre les enjeux réels d'une application traitant des données personnelles. La séparation identité / bulletin de vote est une solution technique et juridique solide.

Points à améliorer

La mise en œuvre technique de certaines mesures de sécurité (chiffrement bout en bout, tokens anonymes) pourrait être approfondie. Si c'était à refaire, j'intégrerais ces contraintes dès la phase de conception.

Objectifs à venir

Approfondir mes connaissances en sécurité applicative web (injections SQL, XSS, CSRF), mieux maîtriser les bonnes pratiques RGPD dans le développement et explorer des frameworks sécurisés pour les applications critiques.

SAÉ4 2025/2026 — Sécurisation & Développement

SAECine — Application web de vote cinématographique

Dans le cadre d'une mise en situation professionnelle simulée, notre ESN DCRS Consulting a été mandatée par Gantois Industries pour auditer, sécuriser et améliorer l'application SAECine — un site web de vote pour des films développé en PHP/MySQL. La mission couvrait la sécurité, la robustesse, la performance, la conteneurisation Docker et l'accessibilité RGAA. J'ai pris en charge les étapes de performance, conteneurisation et accessibilité.

Sécurisation réalisée

  • Fichier .env — credentials BDD externalisés, exclus de Git
  • Hashage bcrypt des mots de passe via password_hash()
  • Protection CSRF sur tous les formulaires POST (token session + hash_equals())
  • Anti brute-force : 5 tentatives / 15 min par IP via session PHP
  • Requêtes préparées PDO avec ATTR_EMULATE_PREPARES = false
  • Gestionnaire d'erreurs global — logs structurés, aucune info technique exposée

Performance & infrastructure

  • Index B-tree sur colonnes de jointure et de filtrage (film, vote, messages)
  • Suppression des SELECT * — colonnes sélectionnées précisément
  • Compression GZIP via mod_deflate Apache (réduction 60-80 %)
  • Cache HTTP mod_expires — CSS 1 semaine, images 1 mois
  • Conteneurisation Docker complète : 3 services (web, db, db_init)
  • Démarrage en 1 commande : docker compose up -d

Robustesse & qualité

  • 129 tests PHPUnit — 100 % de réussite (sécurité, validation, performance)
  • Migration BDD vers InnoDB + utf8mb4 + 4 clés étrangères
  • Conformité RGAA : focus visible, attributs alt, classe .sr-only, contrastes
  • 110 commits sémantiques sur branche develop → Merge Request finale
  • 26 vulnérabilités corrigées — 9/10 objectifs du cahier des charges réalisés

Extrait — Sécurisation & Docker

Deux extraits représentatifs des réalisations : la protection CSRF mise en place sur tous les formulaires POST, et l'architecture Docker qui remplace un environnement WAMP non portable par un démarrage en une seule commande.

PHP csrf.php — Protection CSRF 
// Génération du token (stocké en session)
function csrf_token(): string {
    if (empty($_SESSION['csrf_token'])) {
        $_SESSION['csrf_token'] = bin2hex(random_bytes(32));
    }
    return $_SESSION['csrf_token'];
}

// Champ HTML hidden à insérer dans chaque formulaire
function csrf_field(): string {
    return '<input type="hidden" name="csrf_token"
            value="' . csrf_token() . '">';
}

// Vérification — résistant aux attaques temporelles
function csrf_verify(): void {
    if (!hash_equals($_SESSION['csrf_token'],
                     $_POST['csrf_token'] ?? '')) {
        http_response_code(403);
        exit('Accès refusé');
    }
    unset($_SESSION['csrf_token']); // usage unique
}

Analyse personnelle

Retour sur la SAÉ SAECine

Ce que j'en retiens

Cette SAÉ m'a confronté pour la première fois à une application réelle présentant des vulnérabilités critiques en production. Voir des mots de passe en clair dans une base de données et des credentials codés en dur dans le code source m'a définitivement ancré l'idée que la sécurité doit être pensée dès la conception.

Ressources mobilisées

Cours de développement web, documentation PHP officielle (password_hash, PDO, sessions), documentation Docker et Docker Compose, référentiel RGAA 4, OWASP Top 10 pour la classification des vulnérabilités. J'ai aussi consulté les recommandations WCAG pour les critères de contraste et d'accessibilité.

Points forts

La conteneurisation Docker a été la partie la plus intéressante à résoudre : comprendre pourquoi DELIMITER ne fonctionne pas en dehors du client MySQL interactif, créer un service éphémère db_init pour contourner la non-réexécution du volume — ces problèmes concrets m'ont appris à lire la documentation de fond en comble plutôt que de copier des exemples.

Points à améliorer

HTTPS n'a pas pu être mis en place faute de domaine public dans l'environnement local. Si c'était à refaire, j'aurais anticipé cette contrainte en configurant un reverse proxy NGINX avec un certificat auto-signé pour le développement, en attendant Let's Encrypt pour la production.

Travail en équipe

La répartition des tâches avec Damien Rinaldis était claire dès le départ : il prenait la sécurisation des accès et les tests PHPUnit, je prenais la performance, Docker et le RGAA. Les 110 commits sémantiques sur develop et la Merge Request finale ont simulé un vrai workflow professionnel en ESN.

Objectifs à venir

Mettre en place un pipeline CI/CD GitLab qui exécute automatiquement les 129 tests PHPUnit à chaque push. Ajouter des tests d'intégration couvrant des scénarios utilisateur complets. Explorer PHPStan pour l'analyse statique et Xdebug pour mesurer la couverture de code réelle.
