SAÉ — Systèmes

Mini-Shell en C

Cette SAÉ consistait à développer un interpréteur de commandes (shell) en langage C, capable de gérer des commandes simples, des redirections d'entrée/sortie et des pipes. Le projet s'appuie sur un parseur lexical fourni et une architecture de processus UNIX.

⚙️

Fonctionnalités

  • Prompt dynamique hostname:cwd$
  • Commandes simples avec arguments
  • Builtins cd et set
  • Redirections < > >>
  • Pipe | entre deux commandes
  • Gestion des guillemets
🛠️

Technologies

  • Langage C (C99)
  • Appels système : fork, execvp, waitpid
  • Redirections : dup2, open, pipe
  • Compilation : gcc -Wall -Wextra -O2
  • Environnement Linux / UNIX
🧪

Tests réalisés

  • Commandes simples : echo, pwd, ls
  • Builtin cd avec chemin invalide
  • Builtin set pour variables d'env
  • Redirections >, >>, <
  • Pipe : ls | wc -l
  • Gestion d'erreurs (fichier absent, etc.)

Extrait du code — Mini-Shell

Voici la fonction principale de gestion du pipe, qui illustre l'utilisation de fork, pipe et dup2 pour connecter deux processus.

C exec_pipe — minishell.c 
static int exec_pipe(char *argvL[], char *argvR[]){
  int pfd[2];
  pid_t left, right;

  if (pipe(pfd) < 0){ perror("pipe"); return -1; }

  left = fork();
  if (left == 0){
    dup2(pfd[1], STDOUT_FILENO);
    close(pfd[0]); close(pfd[1]);
    execvp(argvL[0], argvL);
    _exit(127);
  }

  right = fork();
  if (right == 0){
    dup2(pfd[0], STDIN_FILENO);
    close(pfd[0]); close(pfd[1]);
    execvp(argvR[0], argvR);
    _exit(127);
  }

  close(pfd[0]); close(pfd[1]);
  waitpid(left, NULL, 0);
  waitpid(right, NULL, 0);
  return 0;
}

Retour sur la SAÉ Mini-Shell

🖥️ SAÉ Mini-Shell (C / UNIX)

J'ai développé un interpréteur de commandes en C capable de gérer des commandes simples, des redirections et des pipes. La partie la plus formatrice a été l'implémentation de exec_pipe, qui m'a obligé à maîtriser la gestion des descripteurs de fichiers et la synchronisation de processus avec waitpid.

📚 Ressources mobilisées

J'ai utilisé les cours de systèmes d'exploitation (appels système UNIX), ainsi que la documentation man de fork, execvp et dup2. J'ai également consulté des ressources en ligne sur la gestion des processus en C.

💪 Points forts

La gestion des redirections et du pipe m'a permis de bien comprendre le mécanisme de descripteurs de fichiers sous UNIX. J'ai réussi à implémenter l'ensemble des fonctionnalités demandées avec une gestion propre des erreurs.

⚠️ Points à améliorer

La gestion des pipes multiples (chaînes de plus de 2 commandes) n'est pas supportée. Si c'était à refaire, je structurerais le code de façon récursive pour permettre des pipes en cascade.

🎯 Objectifs à venir

Approfondir la gestion des signaux (SIGINT, SIGCHLD), implémenter les pipes multiples et explorer la gestion des variables d'environnement de manière plus complète.

SAÉ — Sécurisation

Déploiement et sécurisation d'un site web

Cette SAÉ consistait à déployer un site web sur un environnement Linux avec un serveur Apache 2, initialement accessible en HTTP, puis à sécuriser les communications en configurant HTTPS via SSL/TLS avec des certificats générés manuellement à l'aide d'OpenSSL.

🌐

Environnement technique

  • Ubuntu 25.10 + navigateur Firefox
  • Serveur web Apache 2
  • Stack LAMP (Linux, Apache, MySQL, PHP)
  • Génération de certificats avec OpenSSL
  • Déploiement via hôte virtuel (VirtualHost)
🔒

Sécurisation HTTPS

  • Activation du module SSL Apache (a2enmod ssl)
  • Génération clé privée RSA + certificat auto-signé
  • Configuration VirtualHost port 443
  • Redirection permanente HTTP → HTTPS
  • Chiffrement SSL/TLS des échanges client-serveur
📋

Résultats obtenus

  • Site accessible via https://sae3.local
  • Connexion chiffrée active (SSL/TLS)
  • Redirection automatique depuis HTTP
  • Avertissement navigateur (certificat auto-signé attendu)
  • Compréhension du rôle des fichiers .key et .crt

Extrait — Configuration HTTPS

Voici la configuration du VirtualHost HTTPS sur le port 443, associant le certificat SSL et la clé privée générés avec OpenSSL, ainsi que la redirection permanente depuis le port 80.

APACHE sae3-ssl.conf 
<VirtualHost *:443>
  ServerName sae3.local
  DocumentRoot /var/www/sae3/public
  <Directory /var/www/sae3/public>
    Require all granted
    AllowOverride All
    DirectoryIndex index.php index.html
    Options -Indexes
  </Directory>
  SSLEngine on
  SSLCertificateFile     /etc/ssl/sae3/sae3.crt
  SSLCertificateKeyFile  /etc/ssl/sae3/sae3.key
  ErrorLog  ${APACHE_LOG_DIR}/sae3_ssl_error.log
  CustomLog ${APACHE_LOG_DIR}/sae3_ssl_access.log combined
</VirtualHost>

<VirtualHost *:80>
  ServerName sae3.local
  Redirect permanent / https://sae3.local/
</VirtualHost>

Retour sur la SAÉ Sécurisation

🔐 SAÉ Sécurisation (Apache / HTTPS)

J'ai déployé un site web sur Apache sous Linux et mis en place une connexion HTTPS en générant manuellement des certificats SSL avec OpenSSL. Cette SAÉ m'a permis de comprendre concrètement pourquoi HTTP seul est insuffisant et comment SSL/TLS garantit la confidentialité et l'intégrité des échanges.

📚 Ressources mobilisées

J'ai mobilisé les cours de réseaux et de systèmes (protocoles HTTP/HTTPS, fonctionnement de SSL/TLS), la documentation Apache et les pages de manuel d'OpenSSL pour la génération des certificats et la configuration du VirtualHost.

💪 Points forts

La génération manuelle des certificats avec OpenSSL m'a donné une compréhension réelle du rôle de la clé privée et du certificat public. La mise en place de la redirection HTTP vers HTTPS et la configuration du VirtualHost ont été réalisées proprement et fonctionnent correctement.

⚠️ Points à améliorer

Le certificat auto-signé provoque un avertissement dans le navigateur, ce qui limite la crédibilité en production. Si c'était à refaire, j'explorerais l'utilisation de Let's Encrypt pour obtenir un certificat reconnu par les autorités de certification.

🎯 Objectifs à venir

Approfondir la configuration de sécurité Apache (en-têtes HTTP de sécurité, désactivation des protocoles obsolètes TLS 1.0/1.1), explorer Let's Encrypt pour des certificats signés, et étudier la mise en place d'un pare-feu applicatif (WAF).

SAÉ4 2025/2026 — Infrastructure & Administration

SAECine — Infrastructure, BDD & Logs

Dans le cadre de la SAÉ4, j'ai pris en charge les aspects d'administration système et d'infrastructure de l'application SAECine : conteneurisation Docker, configuration Apache, migration de la base de données et mise en place d'un système de logs. Ces tâches relèvent directement de la compétence Administrer — déployer, configurer et maintenir un environnement applicatif.

🐳

Conteneurisation Docker

  • Remplacement d'un environnement WAMP local non portable
  • 3 services : web (PHP 8.1 + Apache), db (MySQL 8.0), db_init (éphémère)
  • Import automatique du schéma SQL à chaque docker compose up
  • .dockerignore — exclusion de vendor/, logs/, .env
  • Démarrage complet en 1 commande sur Windows, Linux, macOS
⚙️

Configuration Apache & performance

  • Fichier .htaccess — compression GZIP via mod_deflate
  • Cache HTTP mod_expires — CSS 1 semaine, images 1 mois
  • Index B-tree sur colonnes de jointure et de filtrage
  • Suppression des SELECT * — colonnes sélectionnées précisément
  • Variable APP_ENV — comportement distinct dev / production
🗄️

Migration BDD & logs

  • Migration MyISAM → InnoDB : transactions ACID + clés étrangères
  • Encodage utf8mb3 → utf8mb4 (support Unicode complet)
  • 4 contraintes de clés étrangères (film, vote, jetons, utilisateurs)
  • Gestionnaire d'erreurs global — logs structurés dans logs/app.log
  • Pages d'erreur personnalisées 500 + directive Apache 404

Extrait — Docker & configuration Apache

Deux extraits représentatifs du volet administration : l'architecture Docker mise en place et la configuration .htaccess activant la compression et le cache HTTP.

DOCKER docker-compose.yml — Architecture 3 services 
services:
  web:                          # PHP 8.1 + Apache — port 8080
    build: .
    volumes: [./src:/var/www/html]
    depends_on: [db]

  db:                           # MySQL 8.0 — volume persistant
    image: mysql:8.0
    environment:
      MYSQL_DATABASE: saecine
      MYSQL_ROOT_PASSWORD: ${DB_PASS}
    ports: ["3307:3306"]
    volumes: [db_data:/var/lib/mysql]

  db_init:                      # Service éphémère — import SQL
    image: mysql:8.0            # s'exécute à chaque compose up
    depends_on: [db]
    command: >
      sh -c "mysql -h db saecine < /sql/saecine.sql
             && mysql -h db saecine < /sql/procedures.sql"

# Problème résolu : DELIMITER MySQL non reconnu hors CLI
# → séparation en 2 fichiers SQL distincts
APACHE .htaccess — Compression GZIP & cache HTTP 
# Compression GZIP — réduction 60-80 % des réponses textuelles
<IfModule mod_deflate.c>
  AddOutputFilterByType DEFLATE text/html text/css
  AddOutputFilterByType DEFLATE text/javascript application/javascript
</IfModule>

# Cache HTTP — évite les requêtes inutiles côté navigateur
<IfModule mod_expires.c>
  ExpiresActive On
  ExpiresByType text/css        "access plus 1 week"
  ExpiresByType image/jpeg      "access plus 1 month"
  ExpiresByType image/png       "access plus 1 month"
</IfModule>

# Masquage des erreurs en production
php_flag display_errors Off
ErrorDocument 404 /error_404.php

Analyse personnelle

Retour sur la SAÉ SAECine — volet Administration

🐳 Ce que j'en retiens — Docker

Conteneuriser une application PHP/MySQL pour la première fois m'a confronté à des problèmes concrets d'administration système : la directive DELIMITER non reconnue hors du client MySQL interactif, la non-réexécution du volume Docker après initialisation, l'injection des variables d'environnement depuis docker-compose.yml. Chaque obstacle a nécessité de lire la documentation de fond en comble.

🗄️ Ce que j'en retiens — BDD

La migration de MyISAM vers InnoDB illustre concrètement pourquoi le choix du moteur de stockage a des conséquences réelles : sans InnoDB, impossible d'avoir des transactions ou des clés étrangères. Passer de utf8mb3 à utf8mb4 m'a aussi appris que l'encodage n'est pas qu'un détail technique — c'est une décision d'architecture qui impacte toute la chaîne de traitement des données.

📚 Ressources mobilisées

Documentation officielle Docker et Docker Compose, documentation MySQL 8.0 (moteurs de stockage, clés étrangères, encodage), documentation Apache (mod_deflate, mod_expires), cours de systèmes et réseaux pour la compréhension des mécanismes de cache HTTP et de compression.

💪 Points forts

L'environnement Docker livré permet de démarrer l'application complète en une seule commande sur n'importe quel système. La configuration .htaccess est propre et documentée. La migration BDD est versionnée dans Git et reproductible à chaque docker compose up.

⚠️ Points à améliorer

HTTPS n'a pas pu être configuré dans l'environnement local Docker, faute de domaine public. Si c'était à refaire, j'aurais ajouté un reverse proxy NGINX avec un certificat auto-signé pour le développement — en cohérence directe avec ce que j'ai appris lors de la SAÉ Sécurisation Apache.

🎯 Objectifs à venir

Mettre en place un reverse proxy NGINX avec Let's Encrypt pour la gestion des certificats SSL en production. Explorer GitLab CI pour automatiser le build et le déploiement des conteneurs Docker à chaque push, et ajouter un outil de monitoring des logs applicatifs.
