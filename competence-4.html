SAÉ — Application Web

Coup de Sifflet — Plateforme de vote européenne

Cette SAÉ consistait à concevoir et développer une application web de vote en ligne autour d'équipes de football européennes. L'application gère des scrutins avec périodes de validité, un mécanisme de vote unique par jeton, et des accès différenciés selon les rôles (visiteur, électeur, administrateur).

Fonctionnalités

  • Création et gestion de scrutins par l'administrateur
  • Vote unique via jeton de participation
  • Carte interactive de sélection des pays/équipes
  • Résultats (classement + graphique) après clôture
  • Commentaires publics après clôture du scrutin
  • Redirection automatique selon statut (planifié/ouvert/fermé)

Technologies

  • Stack LAMP (Linux, Apache, MySQL, PHP)
  • Architecture MVC (contrôleurs, DAO, vues)
  • PDO avec requêtes préparées (anti-injection SQL)
  • Carte interactive Leaflet / OpenStreetMap
  • Gestion de sessions PHP pour les rôles

Sécurité & conception

  • Jeton unique par électeur et par scrutin
  • Anonymat : identité dissociée du vote
  • Contrôle de session pour l'accès administrateur
  • Principes SOLID appliqués (SRP, OCP, DIP)
  • Diagrammes UML : cas d'utilisation, classes, séquences

Retour sur la SAÉ Coup de Sifflet

SAÉ Web (Coup de Sifflet)

J'ai participé à la conception et au développement d'une application web de vote complète en PHP/MySQL, avec une architecture MVC, une gestion des rôles et un mécanisme de vote sécurisé par jetons. Ressources mobilisées

J'ai mobilisé les cours de développement web (PHP, SQL, architecture MVC), les cours de conception logicielle (UML, principes SOLID) ainsi que la documentation PDO et la bibliothèque Leaflet pour la carte interactive.

Points forts

La mise en place du mécanisme de jeton pour garantir l'unicité et l'anonymat du vote est la partie dont je suis le plus satisfait. L'architecture DAO centralisée a rendu le code lisible et facilement maintenable, et les requêtes préparées ont sécurisé l'ensemble des accès à la base de données.

Approfondir l'injection de dépendances en PHP, ajouter des statistiques plus avancées sur les résultats (évolution des votes dans le temps, répartition géographique) et améliorer l'interface utilisateur avec un framework CSS moderne.

SAÉ — Probabilités

Étude du surbooking (probabilités)

Cette SAÉ R3.08 modélise le surbooking d'un club de voile. L'idée est d'anticiper les absences grâce à une variable aléatoire binomiale, puis d'évaluer le compromis entre recettes (accepter plus de réservations) et coûts (dédommager en cas de client en trop).

Modélisation

  • Variable aléatoire X — nombre de clients présents
  • X suit une loi binomiale : p = probabilité de présence, n = réservations
  • m = nombre de bateaux disponibles
  • Risque de sous-utilisation : P(X ≤ m-1)
  • Risque de surbooking : P(X ≥ m+1)

Recette attendue

  • Sans surbooking : recette estimée via E(X) et R
  • Avec surbooking : recette intègre remboursements et dédommagements si X > m
  • Objectif : trouver n₀ optimal qui maximise E(R)
  • Résultats comparés : loi binomiale vs approximation normale

Résultats / intérêt

  • Surbooker légèrement augmente les bénéfices
  • Surbooking excessif devient contre-productif (dédommagements)
  • Vérification de la cohérence binomiale vs normale

Analyse personnelle

Retour sur la SAÉ Probabilités

SAÉ Probabilités (surbooking)

J'ai modélisé le nombre de clients qui se présentent avec une loi binomiale, puis j'ai évalué le compromis entre sous-utilisation et surbooking. L'objectif final est de trouver un nombre de réservations optimal n₀ qui maximise la recette moyenne, en intégrant le coût des dédommagements quand X > m.

Points forts (surbooking)

J'ai apprécié la comparaison entre la loi binomiale et son approximation par la loi normale : cela permet de valider la cohérence des résultats et d'expliquer pourquoi, pour des valeurs suffisamment grandes, la normale devient une bonne estimation.

À améliorer (surbooking)

La difficulté principale est d'interpréter correctement les événements (sous-utilisation vs surbooking) et de bien intégrer la formule de recette moyenne avec les termes de remboursements et de dédommagements.

Objectifs (surbooking)

Rendre l'analyse plus décisionnelle (choix du seuil optimal selon le coût réel du dédommagement) et automatiser les calculs et graphes pour tester rapidement plusieurs scénarios.

SAÉ4 2025/2026 — Audit & Gestion de données

SAECine — Audit, BDD & Versionnement

Dans la SAÉ4, le volet Gérer recouvre l'audit de l'application existante, la modélisation et la migration de la base de données, ainsi que la gestion du projet via Git avec une stratégie de branchement et des commits sémantiques. Ces activités — analyser, structurer les données, tracer et coordonner — sont au cœur de la compétence 4.

Audit de l'existant

  • Analyse du code source PHP — architecture, robustesse, sécurité
  • 25 faiblesses identifiées : mots de passe en clair, injections SQL, absence CSRF
  • Classement par gravité : Critique / Haute / Moyenne / Basse
  • Rapport d'audit structuré en 3 axes : sécurité, robustesse, performance
  • Rédaction du cahier des charges et de la proposition commerciale (devis)

Gestion de la base de données

  • Migration MyISAM → InnoDB : transactions ACID activées
  • Encodage utf8mb3 → utf8mb4 (support Unicode complet)
  • Ajout de 4 clés étrangères avec comportements CASCADE / SET NULL
  • Ajout d'index B-tree sur colonnes de jointure et de filtrage
  • Réorganisation des DROP TABLE pour respecter les contraintes FK

Gestion de version Git

  • 110 commits sémantiques sur branche develop
  • Convention Conventional Commits : feat / fix / perf / test / release
  • Merge Request formelle develop → main en fin de projet
  • Stratégie de branchement GitFlow simplifiée
  • 26 vulnérabilités corrigées — 9/10 objectifs du CDC réalisés

Analyse personnelle

Retour sur la SAÉ SAECine — volet Gestion

Ce que j'en retiens — Audit

Auditer une application existante m'a appris à lire du code que je n'ai pas écrit et à identifier des failles que l'auteur n'a pas vues. Classifier chaque faiblesse par gravité et la documenter dans un rapport structuré — comme on le ferait en ESN — est un exercice très différent du développement : il faut être factuel, exhaustif et proposer des solutions concrètes.

Ce que j'en retiens — BDD

La migration BDD a montré concrètement pourquoi le choix du moteur de stockage et de l'encodage a des conséquences réelles sur l'intégrité des données. Sans InnoDB, impossible d'avoir des transactions ou des clés étrangères — et donc impossible de garantir la cohérence entre les tables vote, film et utilisateur.

Ce que j'en retiens — Git

Travailler avec la convention Conventional Commits et une branche develop distincte de main a rendu l'historique Git lisible et professionnel. La Merge Request finale a simulé un vrai processus de revue de code en contexte d'ESN, avec une validation formelle avant fusion en production.

Ressources mobilisées

Documentation MySQL 8.0 (moteurs, encodage, clés étrangères), OWASP Top 10 pour la classification des vulnérabilités, cours de bases de données (modélisation, normalisation, index), documentation Git pour la stratégie de branchement et les conventions de commits.

Points à améliorer

Le cahier des charges a été rédigé après le début des corrections, ce qui n'est pas l'ordre idéal. Si c'était à refaire, je formaliserais d'abord toutes les exigences et les critères de validation avant de toucher au code, pour pouvoir vérifier chaque objectif de manière indépendante.

Objectifs à venir

Mettre en place un pipeline CI/CD GitLab qui exécute automatiquement les tests à chaque push et bloque les Merge Requests si des tests échouent. Explorer les outils d'analyse de la qualité de code (PHPStan, SonarQube) pour automatiser la détection des faiblesses lors de futurs audits.
